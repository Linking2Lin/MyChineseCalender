# 版本管理规则

## 分支和标签

| 名称 | 职责 | 更新规则 |
| --- | --- | --- |
| `master` | 稳定主分支，保存所有正式发布历史 | 通过发布合并更新，当前代码对应最新稳定版本 |
| `dev` | 下一版本的日常开发 | 功能、修复和维护提交汇入此分支 |
| `codex/vX.Y.Z` | 从 `dev` 创建的可选版本开发分支 | 本版开发完成后合回 `dev` |
| `codex/<任务名>` | 从当前版本开发分支创建的可选任务分支，未指定时从 `dev` 创建 | 完成后合回对应开发分支 |
| `release/vX.Y.Z` | 每个正式版本的独立代码分支 | 发布前允许最终修正；封存后不再修改或删除 |
| `vX.Y.Z` | 指向正式发布提交的附注标签，该提交必须属于 `master` 历史 | 发布后不移动、不覆盖、不删除 |

主分支通过 Git 提交历史保存所有正式版本，不在项目中复制多份代码目录。版本分支和标签的提交可以不同，但必须具有相同的文件内容：正常发布时，版本分支指向待发布提交，标签指向将其合入 `master` 的发布合并提交。修复已落后于主分支的旧版本时，标签直接指向旧版补丁分支的发布提交，再将该提交合入主分支历史，具体要求见“已封存版本的修复”。

本项目沿用已有的 `master` 名称。不能在维护过程中自行改名为 `main`，也不能使用重置、变基或强制推送重写正式发布历史。

## 版本号

使用 `X.Y.Z` 三段版本号：

- `X`：重大、不兼容变化，例如影响用户使用方式或持久化兼容的变化。
- `Y`：兼容的功能增加。
- `Z`：兼容的问题修复或维护发布。

应用版本配置位于 `app/build.gradle.kts`：`versionName` 与本次发布版本一致，标签在前面加 `v`。`versionCode` 是独立、严格递增的正整数，每次新版本发布必须大于此前所有已发布版本；从旧版本派生补丁也不能回退。

已封存版本记录：

| 标签 | 版本分支 | versionName | versionCode |
| --- | --- | --- | --- |
| `v1.0.0` | `release/v1.0.0` | `1.0.0` | `1` |

后续发布时在本表添加对应记录，并更新 README 中的最新稳定版本说明。文档应和版本号一起进入发布提交。

## 当前开发版本与启动流程

| 目标版本 | 开发分支 | versionName | versionCode | 状态 |
| --- | --- | --- | --- | --- |
| `1.0.1` | `codex/v1.0.1` | `1.0.1` | `2` | 开发中，尚未创建封存分支和标签 |

`1.0.1` 从 `dev` 的首版代码开始开发。当前版本的日常修改在 `codex/v1.0.1` 进行；需要拆分任务时，从该分支创建 `codex/<任务名>`，完成后合回该分支。`master`、`release/v1.0.0` 和 `v1.0.0` 继续保留首版代码。

开始下一版本时：

1. 核对当前稳定版本、开发分支和用户未提交状态，保留已有改动。
2. 从 `dev` 创建新的 `codex/vX.Y.Z` 版本开发分支。如果 `dev` 已有开发成果，确认这些成果属于本次版本；不得重置 `dev` 到旧标签。
3. 更新 `app/build.gradle.kts` 的 `versionName` 和 `versionCode`，同时更新本节、README 与根目录 AGENTS.md 的开发状态；最新稳定版本记录保持不变。
4. 构建 Debug 和 Release，核对两个 APK 的版本信息，将配置和文档单独提交到开发分支。
5. 开发阶段不提前创建正式版本标签，也不将开发版本合入 `master`。开发完成后，先将版本开发分支合回 `dev`，再执行下方的发布检查与封存流程。

开发状态只描述下一版的目标，不是正式发布记录。完成封存时将本版加入已封存版本表，更新最新稳定版本说明，并清除或更新当前开发状态。

## 发布前检查

1. 查看当前分支和暂存/未提交状态，确定本次要封存的提交。用户已有的其他改动必须保留，不能顺带提交或丢弃；存在这类改动时，应使用隔离工作区完成稳定分支的发布合并。
2. 确认本地与远端没有同名版本分支或标签；核对 `origin/master` 与 `origin/dev` 的状态，不能覆盖远端新增提交。
3. 更新 `versionName`、`versionCode`、本文件版本记录和 README 版本说明，完成提交。
4. 执行仓库现有的发布检查：

   ```sh
   ./gradlew :app:assembleDebug :app:assembleRelease testDebugUnitTest lintDebug :Module_Base:assembleDebugAndroidTest
   ```

   命令包括构建、JVM 测试、Lint 和数据库仪器测试 APK 编译。设备数据库升级测试另见 README；编译仪器测试 APK 不等于执行设备测试。如果环境缺失导致检查无法完成，应明确记录该限制，不能宣称检查通过。

5. 按 README 的建议确认必要的设备验收。源码封存与签名安装包的分发是两个步骤；目前项目没有配置 Release 发布签名。

## 正式封存流程

以下以已经完成提交和验证的 `1.0.0` 为例。执行前工作区应无本次以外的改动；如果用户有其他改动，应在隔离工作区执行合并，保留原工作区状态。

```sh
git switch dev
git branch release/v1.0.0

git switch master
git merge --no-ff release/v1.0.0 -m "release: v1.0.0"
git tag -a v1.0.0 -m "Release v1.0.0"

# 必须无文件差异；标签的提交必须属于主分支历史
git diff --exit-code release/v1.0.0 v1.0.0
git merge-base --is-ancestor v1.0.0 master

# 原子推送：所有引用一起更新，避免只推送了部分发布记录
git push --atomic origin master dev release/v1.0.0 v1.0.0

git switch dev
```

下一次正式发布将上述版本号替换为新版本，例如 `1.1.0`。发布前若在版本分支做了最终修正，必须将修正合回 `dev`，防止后续版本遗漏。只有确认远端引用已更新后，才报告远端封存完成；网络或权限导致推送失败时，保留本地分支和标签并说明待同步状态。

## 已封存版本的修复

不得直接修改已封存的版本分支或移动原标签。例如修复 `1.0.0`：

```sh
git switch -c codex/fix-v1.0.1 v1.0.0
```

修复后将应用版本改为 `1.0.1`，使用大于所有已发布版本的 `versionCode`，更新版本记录并执行检查。创建新的 `release/v1.0.1` 分支，合入 `master` 后打 `v1.0.1` 标签，并把需要的修复同步到 `dev`。如果主分支已发布更高的版本，合并时必须保留当前功能和较高版本号，不能让旧版补丁覆盖最新稳定版；主分支的后续版本另设标签，旧版补丁标签应指向其自身发布分支的提交。

## 查看和继续开发

```sh
# 只查看某个封存版本，处于 detached HEAD 状态
git switch --detach v1.0.0

# 继续当前 1.0.1 版本开发
git switch codex/v1.0.1

# 回到持续开发分支，版本开发成果需先合回此分支
git switch dev

# 查看发布历史
git log --graph --oneline --decorate --all
git tag --list 'v*' --sort=version:refname
```

AI 工具应从根目录 `AGENTS.md` 找到本文件，不能根据当前工作区的版本号猜测发布历史。判断一个版本是否已发布，应核对版本分支、附注标签、主分支历史及远端引用。
